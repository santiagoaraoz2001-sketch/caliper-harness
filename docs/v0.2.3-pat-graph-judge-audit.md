### PAT-004 — confirmed silent field loss and misleading partial success

At **16:21:07**, the model sends one plan call with both `objective` and `execution`. The current phase accepts objective only. `internal/tool/normalize.go:normalizeFields` discards known planning vocabulary that is not a current parameter, treating it as stale. It does not distinguish a historical field from a newly authored future answer. The resulting graph mutation saves the objective with an **empty execution**; the receipt reports success and asks for the method.

The model then sends validation, expecting the method to have been retained; that call fails. It repairs execution, then sends more before supplying validation and fails again. The same two-refusal pattern repeats across risk, progression, presentation and final-check tasks. Session lines415/435,525/545,642/663,780/801 capture the failures; the preceding call_resolution records show the saved blank field.

A second contributing mechanism is confirmed: `planning.go` advertises a stable native plan schema containing **24 optional fields**, while the owning validator allows only the current subset. Actual engine requests contain all24. The prose asks for one current answer, but the native schema appears to permit future fields. `coverage` is absent from the silent-drop vocabulary, so that extra field is rejected while fields such as execution are dropped. This inconsistent recovery helps explain the repeated confusion.

**Required fix:** no silent loss of authored future fields. Align the machine-visible contract with the current step, or use a comparably small stable contract whose accepted field is explicit. A non-current answer must be rejected before effects with a concise exact correction or explicitly preserved under a deliberate contract; do not silently advance multiple steps. Preserve raw authored calls.

**Regression:** objective+execution in an objective phase cannot return ambiguous success while discarding execution; test all known/non-current fields, coverage, invoke/more, missing fields, repeats and stale focus. Prove rendered schema/help and actual validator agree. Replay the four live failure cycles through the real native request path, not just direct function calls.

### PAT-005 — readiness/execution recovery

### Prompt and discoverability causes

Decoded actual engine requests show GraphQL and help available in **all125 inspected valid-run requests**. Knowledge/standards instructions appear in56 and are absent from69. Source confirms why: `internal/agent/context.go:basePrompt` adds `system.coding.knowledge` only for ordinary coding or a claimed execution task, **not guided planning**. Design/architecture decisions are made during that omitted phase. This is a confirmed instruction-coverage gap, though the instruction was present initially and during execution and was still not used.

Graph keys also look like paths. In the separate aborted partial-prompt attempt the model tried `cat caliper/standards/code`; that is direct evidence of naming/lookup confusion, but not part of the valid-run uptake count.

**Repair direction:** put a compact, consistent graph-key and lookup instruction where design decisions happen, reusing the existing help and GraphQL tool. Make the distinction between graph keys and files explicit in the existing example. Avoid dumping guides into every request, forced inventories or another documentation workflow. Evaluate whether maintaining one meaningful identity/capability entry actually reduces later reconstruction and missed wiring.

**Acceptance:** demonstrate an actual model request finding a needed standards section, reading it, creating/updating a relevant project entry and following a reference; verify bounded output, role limits and conflict handling through focused host tests. Zero usage is an uptake failure to investigate, not a license to claim the graph features work empirically or that all graph functionality is broken.

### D1-002 — historical comments defeat the successful-call fast path

`enforcement.go:enforce` skips redundant successful planning/work judgments only when DeliveredUserComments and DeliveredTaskComments are empty. `loop.go:deliveredUserContext` collects all retained delivered comments from continuation history, not only comments newly delivered since the last judgment. Luna's comments remain in the continuation; therefore this guard stays disabled. The changing latest receipt changes the digest, so the identical-packet cache does not solve it.

This is a source-confirmed trigger mechanism consistent with the live cadence, not a measurement of exactly how many calls a repair would save. A deterministic regression must prove one comment is considered once for scheduling, a new comment triggers again, and subsequent successful steps do not keep paying for the old comment. Keep comments in evidence/context; track novelty for scheduling rather than deleting user intent.

### Recommendation: narrow first, evaluate removal

**This run does not demonstrate that always-on advisory D1 earns its cost.** The strongest current candidate is removing or sharply narrowing per-step advisory judgments, while preserving deterministic ownership, scope, schema, checks and outcome handling. Do not remove all decision paths blindly: readiness currently depends on D1 or explicit manual admission, and other authorization/compaction roles have separate contracts. Simply setting decision.disabled would change behavior and introduce human approvals, contaminating a comparison.

For v0.2.3: fix silent PAT field loss and comment-trigger scheduling first; identify every decision path and its actual effect. Use saved evidence for bounded offline decision evaluation, then the already-authorized next fresh benchmark with a clearly recorded reduced-advisory configuration. Compare matched configurations for first runnable artifact, total latency/tokens/memory, actual defects caught, false interventions and final quality. A single paired run is directional evidence, not statistical proof. Keep active run unchanged; no judge removal has been implemented.
