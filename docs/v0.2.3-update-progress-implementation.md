# v0.2.3 updater observability and cancellation

This E10 implementation addresses the observed opaque Windows install/update wait through the existing updater. It does not claim a faster download, skip verification, install a release, or alter user configuration.

## Build

- `internal/update.Manager.Progress` reports the current phase, actual downloaded bytes, known transport total, verified-file count and elapsed time. The phases distinguish checksum fetch, archive download, archive checksum validation, extraction, installed-file verification and storing the verified version. Unknown sizes remain unknown; there is no invented overall percentage or ETA.
- Progress events coalesce chunk/file activity to at most four ordinary updates per second, with immediate phase boundaries. No per-file names or large logs are added.
- TUI progress uses the existing program event mechanism. A single replaceable status row reserves its own screen line and does not add transcript entries. Attempt context identity rejects delayed events from older updates; completion clears the row. Worker activity and configuration-preservation behavior remain independent.
- Cancellation now reaches archive extraction and inventory hashing, not only HTTP. The existing bounded verification worker pool and shared buffers remain. Context checks occur between entries and hash reads; cancellation joins workers before returning. Filesystem syscalls already in progress are not forcefully terminated.
- The npm installer now reports the same meaningful phases, download bytes, known totals and verified-file counts. Chunk updates coalesce to once per second. Interactive stderr updates one row; redirected output records bounded progress lines. Existing explicit npm version selection, prerequisite handling, user-data preservation and custom-prompt behavior are unchanged.

The Go preparation stage still does not activate a version. Old selection is untouched on checksum failure, cancellation or extraction/verification error. Existing staged-folder cleanup remains in place. A verified immutable folder may remain available after a cancellation at the final boundary, but it is never reported as activated.

## Proof

- Full `internal/update` and `internal/bundle` suites pass: `%TEMP%/caliper-v023-update-full-tests.txt`.
- Controlled progress/cancellation and TUI tests pass: `%TEMP%/caliper-v023-update-progress-tests.txt`. The fixtures check actual downloaded byte counts, ordered phases, verified counts, throttling, no activation during Prepare, unchanged previous selection and no abandoned staging directories. They cancel during download, before extraction, inside the extraction reader and after inventory work has begun.
- TUI tests deliver 100 progress events and assert unchanged transcript length, one displayed row and ignored stale/completed-attempt messages.
- `node --test scripts/npm/test.cjs` passes: 13 passed, 3 platform skips, 0 failed in `%TEMP%/caliper-v023-npm-progress-tests.txt`. Progress tests check byte/count accuracy, unknown totals, phases and throttling alongside existing selection/integrity/prerequisite/registration tests.

All network responses used for this verification are controlled local fixtures. No npm publish, GitHub release, real update or Windows security change occurred. End-to-end release artifact installation on all supported operating systems remains a separate qualification gate; these Windows tests do not imply that gate passed.

## Principles

No new user command, model tool, prompt instruction, approval layer or polling model call. Progress and cancellation reuse existing update/event/verification owners. One UI row and bounded callback cadence limit noise and memory. Integrity checks and previous-version preservation remain mandatory. The measured evidence supports observability/cancellation correctness, not speculative speed improvement.
