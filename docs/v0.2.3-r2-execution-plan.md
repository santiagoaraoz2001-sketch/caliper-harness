## Dependency order and ownership

1. **Preserve and reproduce.** Freeze the starting evidence; inspect each failure at its actual owner; retain distinguishing negative controls. No new broad model run while production code changes.
2. **Repair the existing owners in parallel.** Lifecycle owner: current-turn effects, PAT, task/reviewer/check ownership, steering and recovery. Context/knowledge owner: compaction, judge eligibility/capacity/usage, recall, GraphQL and Kuzu. UI/Windows owner: configuration, Setup/model identity, questions/editors/viewers, transport and controller. Parent integrates canonical prompts/guides, complete dispositions, cross-owner behavior, distribution tests and qualification.
3. **Integrate on stable source.** Review interactions, run affected package tests, then one complete Go suite and relevant Python/Node/platform/package checks. Preserve actual exit codes, failures and skip reasons; fix defects and rerun affected checks, then establish a clean full sweep for the final candidate.
4. **Build a distinct candidate.** Record source hashes, executable hash/version, prompt catalog and effective configuration. Never replace the preserved first candidate or installed release.
5. **Requalify without model inference first.** Exercise changed public commands and real Windows terminal/config/process boundaries with isolated fixtures. Test settings inheritance, first-use Setup, model role persistence, question/comment ownership, file/diff behavior, actual tool registry and error handling. No duplicate controllers; reject inference in catalog-only fixtures.
6. **Rerun the harness with Luna as user.** Use a new benchmark workspace/store/session namespace and the original brief/model/provider where comparison is supported. Preserve exact prompt bytes and configuration identities. Luna supplies natural preferences/feedback and tests public features; parent alone sends numbered atomic inputs. No observer implementation hints or benchmark source edits. Bounded output probes answer verification questions; avoid endless gameplay or redesign.
7. **Release decision.** Reconcile all issues, all 33 slash commands and README/SERVER-MODELS flows; review code alongside traces and actual outputs. Report ready only if required gates are supported. A failed or unavailable release gate remains a blocker, not a pass. Publish/install remains a separate action.

## Guiding principles as implementation decisions

| Constraint | Evidence required in the work |
|---|---|
| Simplicity and less work | State which existing ambiguity, duplicate code, repeated call or context is removed. Justify added state/branches; prefer the existing owner. |
| Deterministic host mechanics | IDs, effect ownership, transitions, budgets, receipt freshness and config serialization stay host-owned. No prose keyword classifier pretending to understand arbitrary user intent. |
| Structured, small-model-friendly interaction | Preserve one-field PAT and concise legal next actions; no new giant schema or compulsory checklist. |
| GraphQL/Kuzu foundation | Improve existing relevant retrieval, identity/version history and ownership. No embedding service, speculative index or exhaustive per-symbol inventory. |
| Consistent instructions | Inspect actual role requests, callable help, schemas, errors and validators together. Replace contradictory prose rather than accumulating it. |
| Evidence over claims | Keep submission/commit/uptake, available/implemented/verified and executed/skipped/failed distinct. Missing evidence stays visible. |
| Total burden | For changes to advisory/context behavior, measure calls, bytes/tokens, time, memory and recovery together. Fewer tokens alone is not success. |

No extra judge, reviewer, tool family, review tier or universal code-analysis framework is introduced merely to address the findings. UI/code guidance remains concise and on demand. The guides cannot be marked effective merely because they were edited.

## Concrete acceptance gates

- Read-only, preference and plan-only turns complete without host-invented execution/check obligations. A valid status read of unfinished work is successful; actual mutations/claims still require current verification. This does not claim perfect deterministic interpretation of arbitrary prose before a model acts.
- Feedback persists under the correct owner and applies once across execution/review/interruption; pending/failed delivery remains visible.
- Byte and token capacity failures preserve original context; vacuous compaction cannot silently replace essential intent; expensive unchanged retries are avoided.
- Valid observations and expected negative command outcomes never become schema-repair advice. Successful inspection avoids redundant PAT bookkeeping judgments. Optional native usage is retained without invented estimates.
- Relevant recall has bounded historical provenance; identity updates preserve still-valid preferences; graph/checkpoint failures preserve truthful recoverable state.
- Reviewer tool authority and frozen check-command identity are enforced before execution. Authorized check scripts may themselves write; observed project mutation invalidates review immediately and is not described as OS-level prevention. Required-check adequacy needs meaningful missing-prerequisite/negative controls: an exit-zero receipt alone does not establish assertions or coverage. QA-005/CODE-007 remain open until that evidence exists; no universal output scanner is added. Worker check availability and role contracts must agree.
- Explicit false configuration survives personal/project save-reload. Setup identities, model availability labels, rendering, drafts, scrolling and capture/comment provenance are tested through real UI actions.
- Windows byte fidelity, process ownership, controller publication and recovery work at real boundaries. Environment/dependency failures stay separate from Caliper defects.
- Code-and-trace audit checks actual feature owners, alternate transitions, persistence, repeated effects and meaningful tests. Old artifacts remain untouched.

Distribution/installation/update/rollback and other-platform gates must have explicit evidence or remain release limitations. Do not change security or install real prerequisites simply to turn a skip green; use supported isolated fixtures where sufficient, and report what they cannot establish.

## Integration audit follow-through

Before the final candidate freeze, reconcile each issue row against actual source and test evidence, including retained historical IDs. A category implementation report is insufficient. The cross-owner audit found PROMPT-003 (claimed worker onboarding/duplicate knowledge); candidate review found UI-019 (Setup reverting Manage roles) and CLI-002 (help wording). Per-issue reconciliation also exposed remaining original requirements: CTX-002 replay consumption, GRAPH-005 nested relation vocabulary, RESUME-001 persisted tool view, PAT-013 human approach rendering, CTRL-005 current terminal reconstruction, CTRL-008 isolated installer fixture, and CTRL-010 compaction busy/quit ownership. Each uses the existing owner and focused adverse controls before the final sweep. These are original-scope repairs, not additional runtime review layers.

Run cheap affected-boundary and actual candidate UI checks before spending another complete native suite when feasible. Freeze source for the final complete sweep and retain its manifest. The exact candidate used for the fresh model run must match that source; no model launch until all required local gates pass. An interrupted sweep remains interrupted. Code/help fixes require new candidate identity; historical candidates and their failures remain immutable.

Parallel ownership is a development method: lifecycle, context/knowledge, and UI/Windows build and test within distinct areas; cross-owner audit checks contract consistency and burden; parent integrates and owns the final evidence/decision. Shared file edits are coordinated explicitly. Luna remains the normal user and receives no implementation hints.
