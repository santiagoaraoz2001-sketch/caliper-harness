# v0.3.1 feature register

Status: entry 1 implemented in v0.3.1 (2026-11-18); register retained as
the design record.
Registered: 2026-11-12.

This document records features approved for v0.3.1 so they can be found and
planned later. Each entry states the user intent and the constraints that
any later design must keep.

## 1. Skill conversion tool (`.md` skill to graph)

Convert a conventional Markdown skill file into Caliper's native structures.
The model chooses the conversion target per skill:

- **Domain graph** — the case-specific domain/capability graph format already
  used by the harness: same token limits, same multi-level, multi-jump
  architecture (short stubs with just-in-time elaboration along a path).
- **Workflow** — the workflow-library architecture: a one-step-at-a-time
  workflow in the style of PAT, crafted for the skill's specific purpose
  (versioned blocks composed into a published workflow, executed step by
  step with evidence).

Design constraints (apply to this tool as they do to every Caliper tool):

- The model builds step by step and makes the decisions; it writes only what
  it needs to write, as a self-contained "path" of small authored pieces.
- The complex construction happens programmatically behind the scenes —
  identity, versioning, validation, linking, and publishing are host work,
  never model bookkeeping. This mirrors PAT: the model writes the plan,
  approaches, and tasks; the host binds and maintains the structure.
- Conversion must be lossless in intent: source skill text that does not fit
  the chosen target's fields is preserved and reachable from the path, not
  silently dropped.
- The result must be inspectable and revisable through the same surfaces as
  hand-authored graphs and workflows (no second-class artifacts).

As built: the `convert_skill` tool (run layer) reads the source skill,
records its outline and hash, and opens a draft conversion in the workflow
library store. The model maps one source heading at a time (`add`), then
`publish` refuses while any heading is neither mapped nor explicitly
preserved. Domain publishing writes an index plus one node per piece under
`project/guides/<id>/` through the same domain-budget admission as
hand-authored guides, and requires one worked-example piece and one
negative piece. Workflow publishing creates and publishes one block per
piece plus the composed workflow, without enabling it. The complete
source text is always preserved as `project/skills/<id>/source`, so
unmapped prose stays reachable. The model signals its target choice at
`start` (`domain` or `workflow`); round-trip export back to `.md` is not
supported (the preserved source node is the export).

Open questions for design time (retained from registration):

- How the model signals graph-vs-workflow preference, and whether the host
  may recommend a target from the skill's shape.
- How a large skill is chunked across graph levels without exceeding the
  per-node token limits, and how cross-references inside the skill become
  jumps.
- Round-trip expectations: can a converted artifact be exported back to a
  readable `.md` skill?
