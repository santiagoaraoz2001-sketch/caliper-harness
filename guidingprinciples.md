# Caliper Harness — guiding principles

The purpose is to make small local language models capable of useful, dependable coding through a lightweight harness and a decision model. A feature earns its place by helping that work succeed in normal use.

These principles consolidate Santiago's directions. Read them with [Concept.md](Concept.md), [ConstructionPlan.md](ConstructionPlan.md) §0 and the [settled decisions](verification/2026-10-09-remediation/CONTRACT_DECISIONS.md). Later explicit owner decisions take precedence; historical test results do not establish current readiness.

## Product and implementation

1. **Stay small and understandable.** Simplicity, versatility and capability matter together. An unfamiliar programmer should be able to understand the handwritten code in one afternoon. Prefer a direct function and an existing owner over another framework, service, catalog or ledger. Review readable code and actual responsibility, not line count alone. Avoid accumulating tens of thousands of lines as the default way to add capability.
2. **Make ordinary use easy.** Aim for install, run and useful work with clear recovery when a prerequisite is missing. Discover models the user already acquired. Loading and unloading refer to memory residency and readiness to generate. Keep the in-process Bubble Tea UI and one Go executable; disclose and package its actual native/runtime dependencies.
3. **Help weak executors.** Instruction coherence and specificity are P0: system text, tools, help and examples must agree with actual effects without increasing prompt bloat. Use focused tools, short role instructions, concrete arguments and legal next actions. Advertised tools and arguments come from the final request registry; guided planning presents the current question. Use actual results already in context without demanding a duplicate model query. Preserve explicit partial/unknown effects and user steering in every relevant role handoff. Structured calls and correlated results use the same validated tool registry as explicit text compatibility. Refuse incomplete or malformed effects; never guess corrected arguments or silently downgrade protocols.
4. **Use the graph for organic bookkeeping.** Kuzu is the durable source for product knowledge and Plan→Approach→Task work. Expose the same owning rules through usable GraphQL. Let the model record paths, facts, design documents, expectations and ways of working; keep authored claims distinct from actual tool/check receipts. Ordinary coding without selected PAT uses core tools directly. In selected PAT, finish all current Approach Task briefs before readiness and claim; discovery and bookkeeping remain available during drafting. A real Task claim binds execution to its frozen brief and required checks/review. Draft planning must not hide or disable the core coding toolkit. Optional `plan` guides the complete question-led planning, orchestration, worker, validation, remediation and progress cycle under the agreed lifecycle contract (D46); a flat brief form does not fulfill that workflow.
5. **Give the decision model a concrete progress job.** Specific triggers inspect work, relevant graph updates and product knowledge. Progress includes useful answered questions, selected work, planning, new source information and actual effects; a pending PAT obligation does not erase it. Existing repeat/stall settings schedule advisory check-ins, never impose a call/error ceiling. Supply a consistent programmatic packet with actual user intent, current phase/next action, correlated recent receipts and prior advice. Continue is silent: it sends no message to the model. A supervisory judgment below 0.5 confidence is recorded as failed and supplies no nudge; the executor continues unchanged. This is the owner's explicit advisory confidence rule of 2026-10-14, separate from authorization and readiness thresholds. Other valid directions may nudge toward execution or further deliberation without stopping, discarding, pruning or forcibly restarting reasoning. Deliver those nudges at a natural request boundary that accepts a new message; literal continuation preserves its original input and thought prefix. Long thinking, including 32k or 100k tokens, is not itself failure. Keep inputs within the selected runtime's actual context admission through disclosed selection of optional dense evidence; preserve intent, answers and current failure/phase facts. This packet selection does not prune the worker's context or raw history. Inspection remains available. The sidecar is not an auditor of every coding trace. The host owns identities, actual outcomes and legal transitions; real approval, readiness, check/review, cancellation and dependency/durability contracts remain. A verdict cannot manufacture a passed check, reviewer PASS or completed task. Keep model selection open through compatible decision runtimes.
6. **Keep context lean.** Standard harness overhead, including instructions and advertised tools, should stay below 10,000 tokens and preferably below 5,000. Measure actual requests and identify estimates. Retrieve selected knowledge and brief details on demand; do not repeatedly paste the graph, codebase or full schema. Host system instructions stay outside pruning and compaction and rebuild from their owners on resume. Keep compact callable schemas distinct from fuller help/use cases through the existing help tool: schema lists current tools, schema.<tool> gives its current template, and guide or a named tool supplies comprehensive guidance. Make schema.graphql.<operation> easy to reach; generate signatures from their owners, and load selected documents only on request. Preserve user intent, necessary observations, call/result associations and actual failures through pruning, compaction and resume. Proactive context cleanup is lightweight and deterministic: prune only consumed tool-output bodies more than 50,000 context tokens old, using the configurable age threshold and clearly labelled token estimates. Preserve reasoning, schemas, messages, tool-call/result associations, current information and raw archives; no routine duplicate-exchange or reasoning retirement. It must make no model or decision-model calls. Model-written compaction must be built and available, running automatically at 90% context usage or an explicit user request. Keep raw history addressable separately. This is the owner direction of 2026-10-13 and supersedes earlier broader pruning proposals.
7. **Keep behavior tunable and failure actionable.** Put intended thresholds, limits and switches in YAML. Existing reserved defaults need an owner decision. Errors name what failed and the next useful action. Model parameters and runtime controls must report their real effect or uncertainty.

## Proof and working discipline

8. **Judge capability in realistic small-model use.** Product inference runs on the Mac GPU with models of at most 10B total parameters, except the specifically approved Gemma 4 12B and owner-selected Mellum2.1-12B-A2.5B-Thinking checkpoints. Mellum's 2.5B active size does not erase its 12B total size. Its MXFP4 checkpoint was tested and then deleted at the owner's request; the original BF16 checkpoint was also tested on the Mac GPU, with coding failures and a complete basic converter success preserved. The owner also approved Poolside/Laguna-S-2.1-NVFP4-mlx as a larger-model diagnostic; its approximately118B total parameters remain outside small-model qualification, regardless of its approximately8B active size. Preparation and downloading are not inference evidence. A changed precision or model is not itself evidence of improvement. Use normal sampler and run settings, real projects, actual tools and independently checked artifacts. Record runtime identity and GPU execution. GPU utilization alone is not proof of correctness.
9. **Completion requires execution evidence.** Newly readied coding tasks require a frozen task-specific behavioral command. One actual current verification episode runs that command then the configured project check, and independent reviewer PASS is also required (owner decision D40). Both commands must be approval-visible, later effects invalidate the episode, and older receipts remain historical until explicit readmission. Preserve failed, missing, denied, stale and stopped results. A model's success statement, process exit, test count or database write cannot substitute for the required evidence. A passing existing suite and reviewer assertion do not demonstrate a requested new behavior; review needs actual source/artifact and behavioral evidence, with any missing coverage stated explicitly.
10. **Test the product, not only helpers.** Use meaningful regressions, pre-fix failure controls and independent review for consequential changes, then exercise the real binary/TUI. Include coding, workflows, knowledge recall, context pressure/resume, authorization, settings and first-use scenarios. Keep raw successes and failures; record any intervention. No hidden rescue, mocked model verdict or changed acceptance test may count as a native pass. After every test run or live experiment, show the concise [capability rubric](CapabilityRubric.md), separating component/native evidence, unexercised functions and proven causes from hypotheses, then discuss the result and proposed correction with the owner.
11. **Make each change reviewable.** Fix demonstrated causes, reuse the owning operations, review the entire patch and run the checks appropriate to it. Do not repeatedly run unchanged suites or model attempts without a new hypothesis. Document every turn in ConstructionPlan.md: actions, findings, owner decisions, proposed versus implemented changes, test results and failures, remaining work, and whether a run is active or stopped. Link detailed evidence instead of duplicating raw traces. No placeholders, fabricated success or unchecked completion ticks.
12. **Preserve the user's work.** Keep artifacts, sessions, negative traces and unrelated workloads. Respect existing approval, cancellation and explicit-resume rules. Strict unknown YAML keys remain intentional typo protection. Commit and publish only with owner authorization; the repository is now tracked and the owner has authorized specific publication batches.

The practical acceptance question is: can a small model inspect the right code, make the requested change, run a relevant check, keep its work and product knowledge coherent, and report the actual result without operator rescue?

Owner clarification, 2026-10-14: once a planned task is genuinely claimed, its frozen brief becomes protected system instructions followed by one short shared paragraph explaining actual checks, independent review and the next task/approach handoff. The host carries identities and legal transitions; the model concentrates on the task. Existing progress supervision covers settled ordinary and planned tool batches, including Bash, and actual phase changes. Ordinary coding remains available without a selected plan. These directions do not grant a claim or verification from a prompt.
