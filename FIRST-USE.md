# Caliper Harness: first use on an Apple Silicon Mac

This application folder is a development build. Local relocation is tested; fresh-host installation, public signing and broader coding capability are still being qualified.

Keep the folder intact: `caliper-harness`, `lib/`, `bin/`, `runtime/`, `prompts.yaml`, `python/`, notices and `MANIFEST.sha256` belong together. From that folder, verify the supplied files with `shasum -a 256 -c MANIFEST.sha256`. Place the folder in a permanent location, then run `sh ./install.sh` from inside it. The installer registers `caliper` in `~/.local/bin` and adds that directory to your Bash or Zsh startup files. Open a new terminal, enter your project directory, and run `caliper`. It preserves your working directory and forwards command arguments unchanged. The application stays in the folder you chose; moving it requires running its installer again. Re-running installation updates the launcher without duplicating the PATH entry. For another shell or manual PATH management, use `sh ./install.sh --no-path`; `--bin-dir /absolute/path` selects another command directory. Go and Xcode are builder tools; they are not needed to run the supplied executable. This verification is also automatic: every startup re-hashes all files against `MANIFEST.sha256`, and if only downloadable dependencies (the private Python runtimes or bundled ripgrep) are missing or changed, Caliper warns, names them, and asks a yes/no question before downloading the pinned replacements and re-verifying. Answering no (or pressing Enter) refuses the launch; damage to anything else still requires replacing the complete folder.

## Prepare your project and existing models

Work from the project directory you want the model to edit. Run `caliper` with no arguments. Startup shows the filled white/mint ASCII Specific Labs mark at70columns, scaling down on narrower terminals, followed by real configuration, prompt-catalog and command-availability checks. The full mark takes30rows and startup naturally scrolls on shorter terminals. A pending throbber accompanies work that takes time; `Ctrl+C` cancels startup. Missing tools and service failures remain named rather than appearing ready.

When no worker is configured, Setup opens automatically. Select a Worker, then a Judge, enter an optional project check command, and review before saving. Use up/down and Enter to select. Press `a` on either model page to add an existing server URL or a local checkpoint and launcher. Known launchers provide defaults; custom arguments are optional. In Add, `Ctrl+T` tests the catalog connection and `Ctrl+S` stages the selection. Catalog access does not prove inference or residency. Caliper does not download weights.

Setup saves reusable server/model choices in your user configuration directory. New project settings and state live under `~/Library/Application Support/caliper/workspaces/`, keyed by the canonical project path; existing project-local files and explicitly configured paths remain in use. Explicit model/server sections in a project YAML override those reusable defaults. `/setup` reopens the form; Escape steps back without saving. If a model is missing, start its server and press `r`, or add its location. Local candidates can be loaded in `/status`. Review supports PgUp/PgDn. Saving refuses while active work owns the model or the project configuration has changed outside Setup. See [Server and model connections](SERVER-MODELS.md) for supported runtimes, launch controls and configuration precedence.

For manual configuration, copy the application's `caliper-harness.yaml.example` into the project as `caliper-harness.yaml`, then edit it. If only `specific-harness.yaml` exists, the CLI still selects it; when both exist, `caliper-harness.yaml` takes precedence. An explicit `--config` always selects exactly that path. Unknown YAML keys are rejected with the key name. Paths such as `data/kuzu`, `data/sessions` and `behavior.md` are relative to your working directory. The bundled example omits legacy `templates.path`; the executable finds its shipped `prompts.yaml`.

The self-contained Apple Silicon bundle supplies private standalone Python, pinned MLX worker dependencies, both supported decision adapters and their PyTorch/Transformers dependencies, and ripgrep. Its built-in recipes select those interpreters automatically. Users do not create virtual environments, activate them, run pip or install Homebrew for harness dependencies. macOS supplies Bash. Nothing changes the system Python or your project environment. Explicit custom recipes retain their original interpreter and environment.

Model weights and your project's own check tools remain separate. Use compatible models you already acquired; Caliper does not download replacements. Ollama remains an optional externally installed runtime; the bundled native MLX worker does not require it. Discovery reads the standard Hugging Face and Ollama locations and their environment overrides; add other model roots to `serve.model_dirs`. The pinned worker wheel targets macOS 14 or newer on Apple Silicon. This development folder was checked on this Mac and after relocation; fresh-host/Gatekeeper and native model qualification remain separate.

Set these values to match the runtimes you will use:

- `model.runtime`: `mlx`, `ollama`, or `openai` for a generic compatible server.
- `model.server`: the worker's actual API base, including `/v1` where required.
- `model.name`: the server's actual model identity. An MLX load needs a complete local checkpoint path; an Ollama alias is not an MLX checkpoint.
- `decision.runtime`, `decision.model`, `decision.path` and `decision.server`: the selected judge and its endpoint. Native Laya and System One retain their typed protocols. Compatible chat servers can also serve a judge through validated structured responses; their confidence is model-reported. Decision-trained models are recommended, and an invalid judgment remains a failure.
- `decision.device`: use `gpu` when GPU execution is required and confirm the active device in Status. Checkpoint Python requires your explicit `decision.trust_remote_code` choice.
- `coding.check_command`: a real project check, such as the project's documented test command. The harness records its actual exit status; passing establishes only what that check covers.

For harness-owned MLX loading in the self-contained Mac folder, the default recipe already uses the private worker interpreter. Select a complete compatible local checkpoint in Status and press `l`; no Python configuration is required. Advanced explicit `mlx` recipes still preserve their selected interpreter and native arguments. For an externally managed worker or decision service, start it in its compatible environment and bind the matching endpoint and identity; saving a requested external decision selection does not activate it.

Copy the application’s commented `prompts.yaml` outside its installation folder, then set `prompts.path` to that copy to customize model instructions, tool guidance, decision prompts, reviews and compaction. Only the applicable sections enter context. A new run reads a validated snapshot; its roles keep that snapshot until the run settles. `prompts.path` explicitly selects another complete catalog. Missing keys, invalid interpolation or an absent explicit file refuse by name. Legacy custom template directories must contain the same `prompts.yaml`; standalone `.tmpl` files are no longer active sources. User project facts, actual tool schemas, permissions and verification rules remain owned by the harness.

## Run and inspect

From your project directory, run `caliper`. `caliper help` lists command-line options. The existing explicit form `/absolute/application-folder/caliper-harness tui --config caliper-harness.yaml` remains supported. `/help` lists the current commands. Open `/status` and refresh with `r`. Select a discovered model with the arrow keys: `l` loads it into memory, `u` selects it for the next run, and `x` unloads it under the displayed ownership rules. These actions do not download weights. A listed asset is not proof that its runtime can load it; inspect the actual readiness and error messages.

Ask for a concrete change and its expected behavior. Ordinary coding can inspect, edit and run the declared project check directly. Use the model’s `plan` tool when planning helps or you request a plan. Planned work uses Plan→Approach→Task readiness and claims; qualifying a planned task requires its frozen behavioral check, the project check and independent reviewer PASS. Missing, failed or stale verification remains visible even if the model says it finished. A normally finished thinking-only reply stays in context and the model takes another turn without an added prompt. Managed stops still require explicit resume.

`agent.max_steps: 0` means there is no separate tool-call ceiling. A positive value sets the maximum charged calls; each native array member counts once. Cancellation and configured run time still apply. Progress judgments are advisory: Continue is silent, confidence below 0.5 produces no nudge, and other valid directions preserve reasoning and literal continuation. Remove the obsolete `context.prune_thinking` key from older configurations; proactive context cleanup is deterministic, and model compaction runs at context pressure or on explicit request. File-tool output paging limits govern what enters context, separately from processing a source file.

Deterministic pruning keeps the 50,000-token minimum age for consumed output bodies. It batches eligible replacements when a run starts, its leading instructions or tool definitions change, or context reaches the configured compaction threshold (90% by default). Ordinary tool turns keep prior messages unchanged for prompt-cache reuse. Protected content and raw session history remain intact. Long tasks may retain old outputs until a boundary or context pressure; pruning also runs before the existing full-window check if automatic compaction is disabled.

Use `/settings` to edit supported values, then press `s` to write the YAML. A refused value leaves configuration unchanged. `/sessions` opens recorded work; `/quit` exits normally. Use `/update` to prepare an available release for the next launch, or accept the startup update offer. The running version stays intact. Previous versions, configurations, graphs, sessions and custom prompts are retained. `npm install -g caliper-harness@latest` updates an npm installation. Do not replace the executable alone.

The decision model can be turned off in Settings (`decision.disabled: true`). Required readiness and Risky decisions then ask you directly, and compaction asks you to approve its proposed summary. Checks and independent review remain required. Automatic progress advice and malformed-call recovery are off; an already-owned idle server remains until shutdown or an explicit stop.

If startup or loading fails, read the named missing executable, package, checkpoint or endpoint first. Verify it in the selected environment, then refresh Status. The harness does not silently download a replacement or switch to another model.
